## Verificación en vivo por puente MCP del emulador: 3 bugs cazados y arreglados — DONE [confirmed en emulación real] (2026-07-28)

**Ask (user)**: conducir YO (el agente) el Immersive Web Emulator en su navegador vía el puente MCP `@iwer/extension-bridge` (`.mcp.json`) y verificar el checklist de 9 filas del tutorial de punta a punta, con capturas revisadas. Rama `fix/xr-emulator-input`.

**El puente**: el servidor MCP del harness quedó atascado en "connecting" para siempre (la cadena `cmd /c npx → cmd → node` en Windows rompió el stdio; el proceso vivía y retenía el puerto FIJO 8723 al que marca la extensión). Solución operativa: cliente WS propio contra el relay del bridge — el relay difunde cualquier frame `{id, method}` de un cliente a los demás y devuelve la primera respuesta, y el servidor WS acepta clientes sin cabecera Origin — + un HTTP local conducido con curl; cuando el harness mató a su hijo colgado, bridge propio con `node iwer-bridge.mjs serve`. La extensión remarca sola. Capturas vía `browser_screenshot` a fichero, TODAS miradas antes de afirmar nada. **Trampa operativa**: si la ventana del navegador pierde visibilidad, Chrome congela el rAF de XR y las acciones caducan ("no frame processing the queue") mientras `browser_screenshot` sigue entregando el último frame pintado — se detecta por el error, se cura con `SetForegroundWindow` (script PowerShell), y la captura idéntica-píxel-a-píxel es la pista. `xr_accept_session` solo acepta la sesión OFRECIDA (A-Frame ofrece `immersive-vr`); el botón AR usa `requestSession` → clic humano (AskUserQuestion).

## Retransmisión sólida: carrera de señalización que mataba el broadcast — FIXED [confirmed, harness full-stack con runtime real] (2026-07-26)

**Ask (user)**: al compartir pantalla, el resto veía "conectando…" y luego **"Live sharing stopped"**, en cualquier conexión. "Revisa y haz sólido la retransmisión en todo tipo de conexión."

**Traza de la carrera (línea a línea, confirmada)**: la entidad del screen viaja por la sala (`/codexr-room`, ya conectado) y anuncia `broadcast.active=true` **antes** de que el `broadcast-start` del emisor llegue al socket de broadcast (que se está conectando en ese momento). El espectador manda `viewer-join`; el servidor sin broadcaster respondía `broadcast-stopped/no-signal`; y el handler del espectador hacía `setSharedBroadcastState({active:false})` + **`publishSharedScreenState()`** — un espectador publicaba a toda la sala que el broadcast no existía. Los que iban por delante (con `streamSourceType='remote'` tras `ontrack`) mostraban exactamente `labels.broadcastStopped`; la entidad quedaba inactiva y **nadie reintentaba**.

**Arreglos** (todos estructurales, no parches del síntoma):
1. **Invariante de propiedad**: la entidad de la sala es del emisor. La rama de espectador de `broadcast-stopped` y todos los detach disparados por mensajes de servidor pasan `skipSharedPublish: true` — un espectador solo publica interacciones suyas (drag/resize), jamás campos de broadcast. Test cuenta que el handler tiene exactamente 1 publish y está en la rama del emisor.
2. **Aparcamiento en el servidor**: `registerViewer`/`promoteViewerToRelay` sin broadcaster aparcan (`viewers`/`relayViewers` según ámbito; relay-request siempre al lado relay) y responden `viewer-waiting`; `startBroadcast` sirve a los aparcados — `viewer-join` diferido al emisor por cada local, `relay-start` + **`relay-ready` a cada remoto** (antes faltaba y la rama "waiting" era código muerto). `no-signal` eliminado.
3. **Rejoin que no se autobloquea**: la guarda de `startViewerConnection` solo suprime duplicados **del mismo socket** (`refs.joinAttemptSocket`); watchdog de 5 s reenvía el join si no llegó ni oferta ni `relay-ready` (idempotente gracias al aparcamiento).
4. **El relay es dueño de la sesión**: `startRelayReceiver` cierra las peer connections abandonadas, cancela los watchdogs y fija `activeBroadcasterId`; los handlers de estado ICE se retiran si `refs.relayReceiver` existe — antes el P2P moribundo ejecutaba `detachRemoteBroadcast` → `stopRelayReceiver()` y mataba el relay recién arrancado.
5. **Sin falsos live**: un espectador activo ya no adopta el `broadcastStatus` del snapshot del emisor, y `applySharedScreenState` solo conserva `live` si ese espectador ya lo ganó con su primer fotograma.

**Verificación**: `npm test` 410/410 (2 tests de servidor nuevos: aparcado local+remoto servidos al arrancar sin ningún `broadcast-stopped`, y relay-request temprano aparca; 4 de runtime: invariante de propiedad, `viewer-waiting`+guarda por socket, posesión del relay, no-falso-live). **Harness full-stack** en scratchpad (`broadcastRaceHarness.cjs`): el runtime ensamblado REAL como espectador sobre WebSocket real contra el `HttpServer` real compilado, forzando la carrera — aparcado en `connecting` sin degradar, **cero publicaciones con `broadcast.active=false`**, oferta diferida respondida tras el arranque, y el stop legítimo aterriza como idle.

- **Servidor**: fuera `MAX_RELAY_VIEWERS` y toda la rama `relay-capacity` (también su etiqueta y su rama en el cliente: sin código muerto). El descarte pasa de ciego a **escalonado por capa y por espectador**: >512 KiB de backlog cae la capa alta, >2 MiB caen todos los delta; keyframes, audio y config nunca. Un espectador saturado pierde fluidez y se recupera solo sin arrastrar a nadie.

Títulos con el nombre del servidor. `formatUptime`/`formatElapsed` unificados en `formatDuration`.

## LivePanel server launch fix #2 — shared capability-gated launch — RESOLVED [confirmed]

**Bug**: after fix #1, launching a LivePanel analysis still aborted, now with `historical-comparison-session-unavailable` logged as `SERVER: Error launching http server` / `SESSION_SERVER_MANAGER: Failed to start server` / `NEW_LAUNCHER_LIVEPANEL_ANALYSIS: Server could not be started`.

## Baseline `?`-stripping corruption — RESOLVED [confirmed]

Discovered while validating Chat 2 (LivePanel Dependency Graph Summary): a `?`-stripping corruption traced via `git stash`/`git blame` to commit `87e80c75` ("chore: upload all changes and add Claude Code documentation"), predating Chat 2. Fixed across two sessions; `npm run compile`, `npm run typecheck`, `npm run lint`, and `npm test` (`test:basic`) are all green (0 errors, 305/305 unit tests) as of this snapshot.

- **Root cause pattern**: literal `?` characters were dropped throughout ~20 files by whatever produced commit `87e80c75` — from optional-chaining (`?.` → `.`), ternaries (`cond ? a : b` → `cond a : b`), regex escapes (`\?` inside `/.../` literals), non-capturing groups (`(?:` → `(:`), and even query-string literals (`'?'` → `''`). Some drops are silently-valid-but-wrong JS (a dropped ternary `?` reinterprets the remainder as a no-op labeled statement); others are hard `SyntaxError`s.
- **Fixed (first pass, prior session)**: `src/babia_templates/processing/templateProcessor.ts` — the `candidateFields` boolean-vs-array bug breaking all XR HTML generation.
- **Fixed (this session, full sweep)**: every remaining instance found via `node --check` + `grep` (double-space markers, `\w\.\(` optional-chain markers, `\w\.\[` bracket markers, `^\s*:` continuation lines) across:
  - TS sources: `dependencyGraphService.ts`, `directoryXRParser.ts`, `fileXRParser.ts`, `executePython.ts`, `directoryReAnalyzer.ts`, `reAnalysisManager.ts`, `gitRepositoryService.ts` (including a `split(/\r\n/)` → `split(/\r?\n/)` regex bug that broke Git timeline parsing on LF-only output), `historicalComparisonModels.ts`, `projectEvolutionService.ts`, `collaborationRoomServer.ts`, `httpServer.ts`.
  - Browser runtimes: `codexrCommonRuntime.js`, `codexrVisualStyleRuntime.js`, `analysisModeRuntime.js`, `analysisTableRuntime.js`, `dependencyGraphRuntime.js`, `historicalComparisonRuntime.js`, `projectEvolutionRuntime.js`, `xrChartMappingUiRuntime.js`, `codeXrBoatsRuntime.js` (~340 corruption sites total across these 9 files).
  - `templates/xr/file/xr-visualization.html` (`projectEvolutionRuntime.jsv=${nonce}` → `.js?v=${nonce}`).
  - Test files whose own regex assertions were corrupted the same way: `analysisModeMegatest.test.cjs`, `codeXrBoatsRuntime.test.cjs`, `dependencyGraph.test.cjs`, `historicalComparison.test.cjs`, `historicalComparisonRuntime.test.cjs` region, `projectEvolutionRuntime.test.cjs`, `xrAnalysisTableRuntime.test.cjs`, `xrDataSource.test.cjs`, `reanalysisArchitecture.test.cjs` (the last one updated legitimately — its assertions targeted the *pre-fix* signatures of `executePython.ts`/`reAnalysisManager.ts` options, not corruption).
  - A few adjacent, genuine null-safety gaps surfaced by the same test runs (not literal `?` drops, but revealed once the surrounding code started executing): `resolveControllerView`, `applyControllerView`, `setTableMode` in `analysisModeRuntime.js`; `table.components?.[...]` in `analysisTableRuntime.js`; `state.result?.revision`/`state.result?.bridgeUrl` in `projectEvolutionRuntime.js`.
- **Verification**: `node --check` per file, targeted `node --test` runs per affected suite, then full `npm test` (`typecheck` + `lint` + `compile-tests` + `test:unit`) and `npm run compile` (webpack) — all clean.
- **Residual risk**: this was found and fixed via static analysis + the existing automated test suite, not manual F5/browser verification of every XR mode (Historical Comparison, Project Evolution, Code City boats, dependency-graph XR). Recommend an F5 smoke pass across those modes before release, since some corrupted branches (e.g. deep in `code-xr-boats`, which is paused/out-of-scope for 1.2.0 but was fixed anyway per explicit user request) have no direct test coverage for their exact code paths.
