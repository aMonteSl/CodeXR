## La mesa no se limpiaba: gráfico anterior repintándose encima — FIXED [confirmed, medido antes/después] (2026-07-25)

**Ask (user, 2 capturas)**: "vengo de un bar chart, he cambiado a un barsmap y no se ha limpiado por completo el anterior... la mesa en cualquier análisis que se cambie el gráfico debe primero asegurarse de limpiar bien lo que había antes y luego poner lo nuevo".

**Causa raíz — está en BabiaXR, no en nuestro borrado**: los componentes de gráfico se suscriben al productor de datos vía `NotiBuffer.register(this.processData.bind(this))` guardando `prodComponent`/`notiBufferId`, y **ningún gráfico de babia 1.3.4 declara `remove()`** (verificado descargando `aframe-babia-components@1.3.4`: `bars, barsmap, cyls, cylsmap, pie, doughnut, bubbles, boats` → todos sin `remove`). `NotiBuffer.set()` invoca **todos** los notifiers. Resultado: tras `removeAttribute`, el componente muerto sigue registrado y **repinta su gráfico en la entidad viva** en el siguiente push de datos (cualquier refresco; en la película, cada frame). Nuestro `clearChartComponents`/`clearChartGeneratedChildren` limpiaba bien — y luego el muerto volvía.

**Fixes** (`mappingProfiles.js`): `releaseChartComponentSubscription` da de baja con la API de babia (`prodComponent.notiBuffer.unregister(notiBufferId)`) y anula los handles, invocado por `clearChartComponents` **antes** de cada `removeAttribute`; `releaseChartEntity` expuesto en el runtime y usado por PE (`ensureEvolutionChart` al sustituir, `clearChartVisualization`) y por la comparación (`disposeComparisonGeometry`); y `sweepOrphanChartChildren` + `scheduleOrphanChartSweep` (400/1500 ms) como segunda línea: quita todo hijo que ningún componente vivo reclame (babia cachea sus raíces en `chartEl`/`titleEl`), respetando nodos con `data-codexr-role`.

**Medido (bars→barsmap + push de datos forzado)**: sin arreglo → `chartRoots: 2, orphanRoots: 1, subscribers: 2, meshes: 8`; con arreglo → `1 / 0 / 1 / 4`. Barrido de los 8 gráficos con push: **0 huérfanos y 1 suscriptor** en todos.

**Harness**: ahora modela el contrato productor/consumidor de babia (NotiBuffer real en `babia-queryjson`; los mocks registran y **no** se dan de baja, y repintan reenganchando su raíz), así que esta clase de fuga falla el chequeo en vez de esconderse. Gates: `npm test` 399/399, ambos harness, `compile` — verde.

## LivePanel server launch fix #2 — shared capability-gated launch — RESOLVED [confirmed]

**Bug**: after fix #1, launching a LivePanel analysis still aborted, now with `historical-comparison-session-unavailable` logged as `SERVER: Error launching http server` / `SESSION_SERVER_MANAGER: Failed to start server` / `NEW_LAUNCHER_LIVEPANEL_ANALYSIS: Server could not be started`.

**Root cause**: `HttpServer`'s constructor (`src/servers/runtime/httpServer.ts`) eagerly constructed **all three** session-bound feature services — `HistoricalComparisonService`, `ProjectEvolutionService`, `DependencyGraphService` — for **every** session that carried an `analysisSessionId` (the `ServerLaunchOrchestrator` passes `{ sessionId }` for all modes). **Fix (common, future-proof launch)**: added `src/servers/runtime/analysisServerCapabilities.ts` — a single `resolveAnalysisServerCapabilities(analysisMode)` table declaring, per mode, which optional feature services the shared server attaches (`XR` → all three; `LivePanel` → dependency graph only; `VisualizeDOM` → none; unknown/undefined → none, so a brand-new mode still launches). `HttpServer` now looks up the session mode via `UnifiedSessionRegistry` and constructs each optional service only when its capability is granted. Every analysis mode continues to share the one `MultiServerLauncher` → `HttpServer` launch path; the only per-mode difference is this declarative table. Adding a future analysis type means adding one row here — no launcher/server-core changes. All optional endpoints and refresh handlers already null-guard their services, so a non-attached service degrades gracefully.

**Tests** (`test/analysis/analysisServerCapabilities.test.cjs`, 9 tests): the pure resolver is transpiled and executed to assert the mode→capability contract (including the fresh-copy-per-call guarantee and the unknown-mode default); structural tests assert `HttpServer` resolves capabilities from the session mode and gates each service behind its capability, that the XR-only services are no longer constructed unconditionally, that those constructors are still the throwing kind (so the gate is load-bearing), and that `DependencyGraphService` has no eager `getSession()` and is therefore safe to attach for LivePanel.
