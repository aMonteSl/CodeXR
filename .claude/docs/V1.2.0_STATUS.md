## LivePanel server launch fix — RESOLVED [confirmed]

**Bug**: launching a LivePanel analysis (file or directory) could fail to start its server while the equivalent XR analysis always worked, even though both go through the exact same shared `executeLaunchPipeline` → `SessionServerManager` → `ServerLaunchOrchestrator` → `MultiServerLauncher` chain.

**Root cause**: `LivePanelParser` (`src/code_analysis/engine/parsers/livePanelParser.ts`) was the only parser in the pipeline that did **not** receive the extension's `ExtensionContext`. Every other parser (`FileXRParser`, `directoryXRParser`, `VisualizeDOMParser`) is constructed with `context` and reads `context.extensionPath` directly. `LivePanelParser` was instead constructed with zero arguments (`new LivePanelParser()` in `analysisBootstrap.ts`) and resolved its own template root via a global lookup, `vscode.extensions.getExtension('amonteSl.code-xr')` (note the lowercase id, vs the real `aMonteSl.code-xr` publisher.name) — throwing `Extension amonteSl.code-xr not found` and aborting the whole launch pipeline whenever that lookup didn't resolve in the running extension host. XR/DOM never touched this lookup, so they were never affected.

**Fix**: `LivePanelParser` now takes `context: vscode.ExtensionContext` in its constructor (matching `FileXRParser`/`VisualizeDOMParser`) and resolves templates via `context.extensionPath` directly — no more registry lookup. `AnalysisBootstrap` now constructs it as `new LivePanelParser(context)`.

**Tests** (`test/analysis/livePanelDomIntegration.test.cjs`): one structural test (constructor/field/no-lookup assertions) plus two behavioral tests that actually transpile and execute `livePanelParser.ts` with a stubbed `vscode` module — one confirms the real `templates/analysis_livePanel/{file,directory}` templates load via `context.extensionPath` with zero calls to `vscode.extensions.getExtension`, the other confirms a bad `extensionPath` fails with a clear "Template directory does not exist" error instead of a registry-lookup error. Verified all three fail against the pre-fix code (reproducing `Extension amonteSl.code-xr not found`) via `git stash` before restoring the fix. Full `npm test` (308/308) and `npm run compile` are green.

## LivePanel server launch fix #2 — shared capability-gated launch — RESOLVED [confirmed]

**Bug**: after fix #1, launching a LivePanel analysis still aborted, now with `historical-comparison-session-unavailable` logged as `SERVER: Error launching http server` / `SESSION_SERVER_MANAGER: Failed to start server` / `NEW_LAUNCHER_LIVEPANEL_ANALYSIS: Server could not be started`.

**Root cause**: `HttpServer`'s constructor (`src/servers/runtime/httpServer.ts`) eagerly constructed **all three** session-bound feature services — `HistoricalComparisonService`, `ProjectEvolutionService`, `DependencyGraphService` — for **every** session that carried an `analysisSessionId` (the `ServerLaunchOrchestrator` passes `{ sessionId }` for all modes). But `HistoricalComparisonService` and `ProjectEvolutionService` resolve the session in their constructors (`new GitRepositoryService(this.getSession().targetPath, …)`), and their `getSession()` throws `historical-comparison-session-unavailable` / `project-evolution-session-unavailable` for any session whose `analysisMode !== 'XR'`. So constructing them for a LivePanel session threw inside `new HttpServer(...)` and aborted the shared launch. XR satisfied the check; DOM only escaped by not carrying those services through to endpoints. These are XR-only features that must not be attached to non-XR servers.

**Fix (common, future-proof launch)**: added `src/servers/runtime/analysisServerCapabilities.ts` — a single `resolveAnalysisServerCapabilities(analysisMode)` table declaring, per mode, which optional feature services the shared server attaches (`XR` → all three; `LivePanel` → dependency graph only; `VisualizeDOM` → none; unknown/undefined → none, so a brand-new mode still launches). `HttpServer` now looks up the session mode via `UnifiedSessionRegistry` and constructs each optional service only when its capability is granted. Every analysis mode continues to share the one `MultiServerLauncher` → `HttpServer` launch path; the only per-mode difference is this declarative table. Adding a future analysis type means adding one row here — no launcher/server-core changes. All optional endpoints and refresh handlers already null-guard their services, so a non-attached service degrades gracefully.

**Tests** (`test/analysis/analysisServerCapabilities.test.cjs`, 9 tests): the pure resolver is transpiled and executed to assert the mode→capability contract (including the fresh-copy-per-call guarantee and the unknown-mode default); structural tests assert `HttpServer` resolves capabilities from the session mode and gates each service behind its capability, that the XR-only services are no longer constructed unconditionally, that those constructors are still the throwing kind (so the gate is load-bearing), and that `DependencyGraphService` has no eager `getSession()` and is therefore safe to attach for LivePanel. Full `npm test` (317/317) and `npm run compile` are green.
