# CodeXR Code City XR

## Purpose

`codexr-code-city` is the first CodeXR-owned replacement for the old
`babia-boats` default city chart. It keeps the same core idea: a software city
where buildings represent code elements and districts represent hierarchy, but
the runtime, rendering, interaction and lifecycle are now owned by CodeXR.

The chart id exposed by the VS Code UI is `code-city`, and the A-Frame
component is `codexr-code-city`.

## Why CodeXR Owns This Chart

CodeXR 1.2.0 starts reducing runtime dependency on BabiaXR. Babia charts remain
available as legacy options, but new visual behavior should live in CodeXR
components so it can evolve without modifying third-party repositories.

This work introduced the shared component tree under:

```text
src/codexr-components/
  graphs/
    common/
    code-city/
    dependency-graph/
  others/
```

`graphs/common` contains reusable XR graph helpers:

- floating tooltip with the dependency graph visual style;
- billboard behavior facing the camera;
- common picking hitboxes;
- metric scaling helpers;
- compact text helpers;
- flat material palettes;
- transform animation helpers.

Dependency Graph and Code City both use this shared layer.

## Data Contract

Code City consumes the existing `data.json` generated by CodeXR. The analyzer
format does not change.

Directory/project analysis:

- buildings represent files;
- districts represent directories;
- nested directories become nested districts;
- the default mapping matches the previous Boats default:
  - `Area = functionCount`
  - `Height = totalLines`
  - `Color = cyclomaticComplexityNumber`

File analysis:

- buildings represent functions or methods;
- districts represent classes, modules or a fallback file/module container;
- the default mapping matches the previous Boats default:
  - `Area = parameters`
  - `Height = lineCount`
  - `Color = complexity`

## Layout

The city uses a recursive treemap layout:

1. Build a stable tree from normalized record paths.
2. Compute directory weights from files/functions and nested children.
3. Allocate district rectangles using a squarified layout.
4. Use a grid fallback for dense groups of leaf buildings.
5. Apply gutters and insets so buildings do not touch district borders.
6. Raise districts by depth, creating stepped terraces like a city model.
7. Place every building on the final district terrace that owns it.

Parent directories stay low. Child directories rise progressively. This makes
the hierarchy readable from a distance and keeps the relationship between
directories and buildings visible.

## Rendering

The visual model is deliberately opaque and stable. It avoids transparent rings
or large translucent slabs that can shimmer in XR.

Code City renders:

- a global dark city base with a bright outer rail;
- solid district terraces with luminous borders;
- procedural street lines inside districts;
- building plots;
- building bodies;
- roofs;
- roof ridges;
- repeated front and side window rows;
- facade ribs;
- age/change markers.

The building color remains the dominant data color. Procedural facade elements
are tints and shadows derived from that color, so texture improves legibility
without stealing the encoded metric.

No external texture assets are loaded.

## Interaction

All visible buildings and districts have shared CodeXR hitboxes. Hover and click
use the common tooltip component:

- hover shows the tooltip temporarily;
- click pins the tooltip;
- clicking the same element again releases it;
- tooltips are placed above the computed city bounding box or above the target,
  whichever is higher;
- the tooltip billboards toward the user camera.

District tooltips show path, depth, item count, child count and aggregate
weight. Building tooltips show path, mapped metrics, language/type and change
state when available.

## Mapping

Code City supports the same user-facing mapping dimensions as Boats:

- `Area`: numeric metric controlling footprint.
- `Height`: numeric metric controlling building height.
- `Color`: numeric or categorical metric controlling color.

Mapping changes are reconciled by stable ids. Existing buildings and districts
interpolate position, size, height, color and texture placement. New elements
fade/scale in, removed elements fade/scale out.

The default transition is 900 ms with `easeInOutCubic`. This is intentionally
slower than the first prototype so metric changes read as a spatial transition
instead of a pop.

Invalid mappings do not clear the city. The component reports invalid geometry
and keeps the previous valid visual state so Field Mapping can roll back.

## Analysis Surface Lifecycle

Code City renders inside the single CodeXR analysis surface. Pressing `V` to
open `Visualization mode` always:

1. Saves the current mode state.
2. Disables mode-specific raycasters.
3. Clears the analysis surface.
4. Shows the orange selector table.
5. Keeps data and mode memory available for later restoration.

This is not specific to Code City. Any future CodeXR chart must render inside
the same surface and use the same lifecycle contract.

## Field Mapping Safety Fix

During 1.2.0 testing, a hidden `Visualization mode` option could still receive
raycaster clicks after the mapping panel was rebuilt. That made clicks near the
center of Field Mapping unexpectedly open Historical Comparison.

The fix is general:

- visualization mode buttons no longer start with `babiaxraycasterclass`;
- the mapping panel enables raycast classes only for the visible view;
- rebuilt mapping rows are explicitly disabled when Mapping is not active;
- mode option clicks are ignored unless the active panel view is actually
  `visualization-mode`.

This protects current and future panel views from hidden hitboxes.

## Debugging

`CodeXRDebug.status()` reports the active mode, visual surface and renderer
state. `codexr-code-city` also exposes a local debug snapshot with:

- component name;
- inferred analysis mode;
- record count;
- current mapping;
- district count.

The browser console uses `[CodeXR.Debug]: ...` for lifecycle traces.

## Tests

The 1.2.0 test coverage includes:

- file/directory mode inference;
- nested path and district tree creation;
- stepped district terraces;
- dense building containment;
- city bounds used for title and tooltip placement;
- invalid mapping rollback behavior;
- procedural facade and district texture markers;
- animation duration and easing;
- shared tooltip/hitbox helpers;
- hidden panel raycaster prevention.

Manual validation should include:

- directory and file analyses with `code-city` as default;
- changing Area, Height and Color repeatedly;
- hover and pin on buildings and districts;
- opening `Visualization mode` from normal mapping;
- switching through normal, dependency graph and historical comparison;
- confirming the city disappears cleanly from the selector and restores cleanly
  when returning to normal analysis.

## Future Work

Prepared but not yet exposed in the UI:

- age as a configurable visual dimension;
- churn and Git activity;
- risk scoring;
- density of functions per file;
- richer facade grammars per language or status;
- renderer instancing for very large cities.

Babia Boats remains available as a legacy chart while Code City matures.
